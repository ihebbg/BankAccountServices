CQRS et MediatR
avec le métier Customer

Une progression adaptée à BankAccountServices : Repository Pattern, sans couche CustomerService, d’abord sans MediatR puis avec MediatR.

Objectif : comprendre le rôle du Controller, des Commands, des Queries, des Handlers, du Repository et de MediatR — puis savoir les assembler sans duplication.

1. L’idée essentielle de CQRS

CQRS signifie Command Query Responsibility Segregation. Il sépare les opérations qui modifient l’état des opérations qui lisent l’état.

CommandQuery
Demande une modificationDemande une information
Create, Update, DeleteGetById, GetAll, Search
Peut lire avant d’écrireNe doit pas modifier les données
Ex. AddCustomerCommandEx. GetCustomerByIdQuery
Important : CQRS n’oblige ni MediatR, ni plusieurs bases, ni la Clean Architecture. Une seule application et une seule base peuvent parfaitement utiliser CQRS.

Application au métier Customer

Commands                         Queries
AddCustomer                     GetCustomerById
UpdateCustomer                  GetCustomers
DeleteCustomer                  GetPaginatedCustomers

2. Architecture retenue dans ce projet

Le Repository Pattern existant est conservé. Les Handlers remplacent progressivement les méthodes de CustomerService.

Controller → CommandHandler / QueryHandler → ICustomerRepository → CustomerRepository → Base

Le Controller gère HTTP. Le Handler réalise un cas d’utilisation. Le Repository encapsule l’accès aux données.

Arborescence compacte

Features/
└── Customers/
    ├── Commands/
    │   ├── AddCustomerHandler.cs
    │   ├── UpdateCustomerHandler.cs
    │   └── DeleteCustomerHandler.cs
    └── Queries/
        ├── GetCustomerByIdQueryHandler.cs
        └── GetCustomersQueryHandler.cs

Controllers/CustomerController.cs
Repositories/Interfaces/ICustomerRepository.cs
Repositories/CustomerRepository.cs
Helpers/PositiveNumberValidationHelper.cs
Pour limiter le volume de code pendant l’apprentissage, une demande et son Handler peuvent vivre dans le même fichier. La règle importante reste : un Handler par opération.

3. Version sans MediatR

Le Controller injecte directement chaque Handler et appelle Handle().

Query : lire un Customer

public record GetCustomerByIdQuery(long CustomerId);

public class GetCustomerByIdQueryHandler(
    ICustomerRepository repository,
    IMapper mapper)
{
    public CustomerResponseDTO Handle(GetCustomerByIdQuery query)
    {
        PositiveNumberValidationHelper.Validate(
            query.CustomerId,
            nameof(query.CustomerId));

        var customer = repository.GetCustomer(query.CustomerId)
            ?? throw new KeyNotFoundException("Customer introuvable.");

        return mapper.Map<CustomerResponseDTO>(customer);
    }
}

Command : créer un Customer

public record AddCustomerCommand(string Name, string Email);

public class AddCustomerCommandHandler(
    ICustomerRepository repository)
{
    public Retour Handle(AddCustomerCommand command)
    {
        var email = command.Email.Trim().ToLowerInvariant();

        if (repository.CustomerEmaiLExist(email))
            throw new InvalidOperationException("Email déjà utilisé.");

        var customer = new Customer
        {
            Name = command.Name.Trim(),
            Email = email
        };

        var id = repository.AddCustomer(customer);

        return new Retour
        {
            Code = CodeRetour.Ok,
            Message = "Customer ajouté",
            ID = id
        };
    }
}
Pourquoi la Command lit-elle l’email ? Une Command peut lire pour vérifier une règle métier avant d’écrire. Elle reste une Command car son objectif final est la création.

Controller sans MediatR

[ApiController]
[Route("api/[controller]")]
public class CustomerController(
    AddCustomerCommandHandler addHandler,
    GetCustomerByIdQueryHandler getByIdHandler)
    : ControllerBase
{
    [HttpPost]
    public ActionResult<Retour> Add(CustomerCreateDTO input)
    {
        var command = new AddCustomerCommand(input.Name, input.Email);
        return Ok(addHandler.Handle(command));
    }

    [HttpGet("{idCustomer:long}")]
    public ActionResult<CustomerResponseDTO> GetById(long idCustomer)
    {
        var query = new GetCustomerByIdQuery(idCustomer);
        return Ok(getByIdHandler.Handle(query));
    }
}

Enregistrement sans MediatR

builder.Services.AddScoped<AddCustomerCommandHandler>();
builder.Services.AddScoped<GetCustomerByIdQueryHandler>();

4. Où passe la couche Services ?

Dans cette architecture, chaque Handler est déjà un service applicatif spécialisé. Un gros CustomerService contenant toutes les opérations ferait doublon.

AvantAprès migration CQRS
CustomerService.AddCustomer()AddCustomerCommandHandler.Handle()
CustomerService.UpdateCustomer()UpdateCustomerCommandHandler.Handle()
CustomerService.DeleteCustomer()DeleteCustomerCommandHandler.Handle()
CustomerService.GetCustomerByID()GetCustomerByIdQueryHandler.Handle()
À éviter : Controller → Handler → CustomerService → Repository. Le Handler et le service porteraient la même responsabilité.

Quand garder un service ?

  • Service technique : JWT, S3, e-mail, SMS, fournisseur de paiement.
  • Règle partagée : calcul de frais bancaires utilisé par plusieurs Handlers.
  • Intégration externe : appel à une API ou à un système tiers.
TransferMoneyCommandHandler
├── IBankAccountRepository
├── ITransactionFeeService
├── IPaymentService
└── INotificationService

5. Validation et erreurs

Une règle répétée peut être centralisée dans un helper :

public static class PositiveNumberValidationHelper
{
    public static void Validate(long value, string parameterName)
    {
        if (value <= 0)
            throw new ArgumentOutOfRangeException(
                parameterName,
                value,
                "La valeur doit être strictement positive.");
    }
}

Utilisation :

PositiveNumberValidationHelper.Validate(
    command.CustomerId,
    nameof(command.CustomerId));

Le GlobalExceptionMiddleware transforme ensuite les exceptions en réponses HTTP cohérentes.

Unicité de l’e-mail

La vérification du Repository améliore le message métier, mais une contrainte UNIQUE en base reste indispensable contre deux créations simultanées.

6. Pourquoi ajouter MediatR ?

Sans MediatR, un Controller important finit par injecter de nombreux Handlers. Avec MediatR, il injecte seulement ISender et envoie chaque demande.

Controller → sender.Send(request) → MediatR → Handler correspondant → Repository
Sans MediatRAvec MediatR
Injection de chaque HandlerInjection d’un seul ISender
Appel direct de Handle()Appel de Send()
Enregistrement manuelDécouverte automatique des Handlers
Traitements transversaux manuelsPipeline Behaviors

MediatR ne remplace ni CQRS, ni le Handler, ni le Repository. C’est un médiateur en mémoire.

Installation et configuration

dotnet add package MediatR

Dans Program.cs :

builder.Services.AddMediatR(config =>
    config.RegisterServicesFromAssemblyContaining<Program>());

Query et Handler avec MediatR

using MediatR;

public record GetCustomerByIdQuery(long CustomerId)
    : IRequest<CustomerResponseDTO>;

public class GetCustomerByIdQueryHandler(
    ICustomerRepository repository,
    IMapper mapper)
    : IRequestHandler<GetCustomerByIdQuery, CustomerResponseDTO>
{
    public Task<CustomerResponseDTO> Handle(
        GetCustomerByIdQuery query,
        CancellationToken cancellationToken)
    {
        PositiveNumberValidationHelper.Validate(
            query.CustomerId,
            nameof(query.CustomerId));

        var customer = repository.GetCustomer(query.CustomerId)
            ?? throw new KeyNotFoundException("Customer introuvable.");

        var result = mapper.Map<CustomerResponseDTO>(customer);
        return Task.FromResult(result);
    }
}

Controller avec MediatR

public class CustomerController(ISender sender) : ControllerBase
{
    [HttpGet("{idCustomer:long}")]
    public async Task<ActionResult<CustomerResponseDTO>> GetById(
        long idCustomer,
        CancellationToken cancellationToken)
    {
        var query = new GetCustomerByIdQuery(idCustomer);
        var result = await sender.Send(query, cancellationToken);
        return Ok(result);
    }
}

7. Pipeline Behaviors

Les Behaviors exécutent automatiquement des traitements avant et après tous les Handlers.

HTTP → LoggingBehavior → ValidationBehavior → Handler → Repository

Cas d’usage fréquents :

  • validation des Commands et Queries ;
  • journalisation et corrélation ;
  • mesure des performances ;
  • transactions ;
  • cache des Queries ;
  • contrôle d’autorisation.
C’est le principal avantage architectural de MediatR. On évite de recopier le même code transversal dans tous les Handlers.

8. Règles pratiques à retenir

  1. Une Command exprime une intention de modification.
  2. Une Query lit sans modifier.
  3. Un Handler traite une seule opération.
  4. Une Command peut lire pour valider avant d’écrire.
  5. Un Handler ne devrait généralement pas appeler un autre Handler.
  6. CommandHandler et QueryHandler utilisent directement les repositories nécessaires.
  7. La logique partagée ou externe va dans un service spécialisé.
  8. MediatR est optionnel ; CQRS fonctionne sans lui.
  9. Ne pas appliquer CQRS mécaniquement à un CRUD trop simple.

Erreurs fréquentes

9. Plan de migration Customer

  • Créer GetCustomerByIdQueryHandler.
  • Créer GetCustomersQueryHandler.
  • Créer AddCustomerCommandHandler.
  • Créer UpdateCustomerCommandHandler.
  • Créer DeleteCustomerCommandHandler.
  • Enregistrer les Handlers dans l’injection de dépendances.
  • Modifier CustomerController pour appeler les Handlers.
  • Supprimer chaque ancienne méthode migrée de CustomerService.
  • Supprimer ICustomerService et CustomerService une fois vides.
  • Compiler et tester chaque route après chaque petite migration.
  • Ajouter MediatR seulement après avoir compris les appels directs.
