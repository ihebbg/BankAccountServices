1. Qu’est-ce qu’Amazon ECR ?

Amazon Elastic Container Registry est un registre managé pour stocker, versionner, analyser et distribuer des images de conteneurs Docker/OCI.

TermeDéfinition
RegistryRegistre régional associé à un compte AWS : COMPTE.dkr.ecr.REGION.amazonaws.com.
RepositoryCollection logique d’images d’une application, par exemple bankaccount-api.
ImageArtefact immuable composé de couches.
TagAlias lisible comme v1.4.2 ou commit-a1b2c3.
DigestIdentifiant cryptographique immuable sha256:....
ECR stocke les images ; il ne les exécute pas. ECS, EKS, EC2, Lambda ou App Runner exécutent les conteneurs.

2. ECR privé et ECR public

ECR PrivateECR Public
Images accessibles via IAM et repository policies, destinées aux workloads privés d’une organisation.Images publiées pour une consommation publique, avec un catalogue public.

Pour une API bancaire .NET, utiliser normalement un repository privé.

3. Créer un repository

aws ecr create-repository \
  --repository-name bankaccount-api \
  --region us-east-1 \
  --image-tag-mutability IMMUTABLE \
  --image-scanning-configuration scanOnPush=true

URI obtenue :

652197205619.dkr.ecr.us-east-1.amazonaws.com/bankaccount-api

Choix recommandés

  • Tags immuables pour empêcher l’écrasement d’une version.
  • Scan activé ; Enhanced Scanning avec Amazon Inspector en production.
  • Chiffrement AES-256 ou KMS selon les exigences.
  • Lifecycle policy pour supprimer les images anciennes.
  • Tags AWS : application, environnement, propriétaire et coût.

4. Construire l’image ASP.NET Core

Exemple de Dockerfile multi-stage :

FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src
COPY BankAccountServices.csproj ./
RUN dotnet restore
COPY . .
RUN dotnet publish -c Release -o /app/publish --no-restore

FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS runtime
WORKDIR /app
ENV ASPNETCORE_URLS=http://+:5000
EXPOSE 5000
COPY --from=build /app/publish .
ENTRYPOINT ["dotnet", "BankAccountServices.dll"]

Construire et tester :

docker build -t bankaccount-api:local .
docker run --rm -p 5000:5000 \
  --env ASPNETCORE_ENVIRONMENT=Production \
  bankaccount-api:local

curl http://localhost:5000/api/Customer/liste

Bonnes pratiques image

  • Utiliser un build multi-stage et une image runtime minimale.
  • Épingler les versions de base et reconstruire régulièrement.
  • Ne pas copier les secrets dans l’image.
  • Ajouter un fichier .dockerignore.
  • Exécuter avec un utilisateur non-root lorsque possible.
  • Scanner les dépendances et l’image finale.

5. Authentification Docker auprès d’ECR

Le principal IAM doit avoir ecr:GetAuthorizationToken. Connexion :

aws ecr get-login-password --region us-east-1 |
docker login \
  --username AWS \
  --password-stdin \
  652197205619.dkr.ecr.us-east-1.amazonaws.com

Le mot de passe temporaire ne doit pas être enregistré dans Git ou affiché dans les logs.

6. Taguer et pousser l’image

ACCOUNT_ID=652197205619
REGION=us-east-1
REPOSITORY=bankaccount-api
VERSION=1.0.0

docker tag bankaccount-api:local \
  $ACCOUNT_ID.dkr.ecr.$REGION.amazonaws.com/$REPOSITORY:$VERSION

docker push \
  $ACCOUNT_ID.dkr.ecr.$REGION.amazonaws.com/$REPOSITORY:$VERSION

Ajouter aussi un tag de commit facilite la traçabilité :

VERSION=$(git rev-parse --short HEAD)
En production, déployer un tag versionné ou, mieux, un digest. Éviter de dépendre uniquement de latest, dont le contenu peut changer.

7. Pull et exécution sur EC2

Attacher à EC2 un IAM Role permettant de lire le repository. Ne pas placer de clés AWS sur le serveur.

aws ecr get-login-password --region us-east-1 |
docker login --username AWS --password-stdin \
  652197205619.dkr.ecr.us-east-1.amazonaws.com

docker pull \
  652197205619.dkr.ecr.us-east-1.amazonaws.com/bankaccount-api:1.0.0

docker run -d \
  --name bankaccount-api \
  --restart unless-stopped \
  -p 127.0.0.1:5000:5000 \
  --env-file /etc/bankaccount.env \
  652197205619.dkr.ecr.us-east-1.amazonaws.com/bankaccount-api:1.0.0

Nginx ou un ALB expose ensuite l’application, tandis que le port conteneur reste privé.

8. Permissions IAM

Permissions minimales pour pull

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "ecr:GetAuthorizationToken",
      "Resource": "*"
    },
    {
      "Effect": "Allow",
      "Action": [
        "ecr:BatchCheckLayerAvailability",
        "ecr:GetDownloadUrlForLayer",
        "ecr:BatchGetImage"
      ],
      "Resource": "arn:aws:ecr:us-east-1:652197205619:repository/bankaccount-api"
    }
  ]
}

Permissions supplémentaires pour push CI/CD

ecr:InitiateLayerUpload
ecr:UploadLayerPart
ecr:CompleteLayerUpload
ecr:PutImage

Les repository policies sont des politiques basées sur la ressource. Elles servent notamment à autoriser un autre compte AWS à lire un repository.

Pour un accès cross-account, il faut généralement une autorisation côté repository et une autorisation IAM côté principal externe.

9. Tags immuables et digests

Avec l’immutabilité, pousser une nouvelle image sous un tag existant échoue. Cette protection évite qu’un artefact approuvé change silencieusement.

# Tag humain
bankaccount-api:1.0.0

# Tag traçable
bankaccount-api:commit-a1b2c3d

# Référence immuable
bankaccount-api@sha256:abcdef...

10. Scan des vulnérabilités

Basic scanningEnhanced scanning
Analyse des vulnérabilités de l’image selon la configuration ECR.Intégration Amazon Inspector, analyse automatisée et continue des packages OS et langages.
aws ecr start-image-scan \
  --repository-name bankaccount-api \
  --image-id imageTag=1.0.0

aws ecr describe-image-scan-findings \
  --repository-name bankaccount-api \
  --image-id imageTag=1.0.0

Une pipeline peut bloquer la promotion en production lorsqu’une vulnérabilité critique non acceptée est détectée.

11. Lifecycle Policy

Exemple : conserver seulement les 20 dernières images taguées release-*.

{
  "rules": [{
    "rulePriority": 1,
    "description": "Conserver 20 releases",
    "selection": {
      "tagStatus": "tagged",
      "tagPrefixList": ["release-"],
      "countType": "imageCountMoreThan",
      "countNumber": 20
    },
    "action": { "type": "expire" }
  }]
}

Toujours exécuter la preview avant d’appliquer une lifecycle policy. Les images éligibles sont ensuite expirées automatiquement.

Ne pas supprimer une image encore référencée par ECS, un Launch Template, une procédure de rollback ou un environnement rarement redéployé.

12. Déploiement avec ECS

ECR image → ECS Task Definition → ECS Service → Tasks Fargate/EC2 → ALB Target Group
  1. La pipeline pousse une nouvelle image ECR.
  2. Elle crée une nouvelle révision de Task Definition.
  3. Le service ECS lance les nouveaux tasks.
  4. L’ALB attend leurs health checks.
  5. ECS retire progressivement les anciens tasks.

Le Task Execution Role permet à ECS de tirer l’image et d’écrire les logs. Le Task Role donne à l’application ses permissions métiers, par exemple S3.

Séparer Task Execution Role et Task Role est une réponse importante en entretien.

13. CI/CD avec GitHub Actions

Push Git → tests → docker build → scan → login ECR → push → déploiement ECS/EC2
permissions:
  id-token: write
  contents: read

steps:
  - uses: actions/checkout@v4

  - uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: arn:aws:iam::652197205619:role/github-ecr-push
      aws-region: us-east-1

  - uses: aws-actions/amazon-ecr-login@v2

  - run: |
      IMAGE=652197205619.dkr.ecr.us-east-1.amazonaws.com/bankaccount-api:${GITHUB_SHA}
      docker build -t "$IMAGE" .
      docker push "$IMAGE"

OIDC permet à GitHub d’assumer temporairement un rôle AWS, sans stocker une access key permanente dans les secrets GitHub.

14. Réplication et haute disponibilité

ECR peut répliquer des images :

  • vers une autre région pour reprise après sinistre ou proximité ;
  • vers un autre compte pour séparer build, recette et production.

La réplication s’applique aux nouvelles images après configuration. Les politiques repository et lifecycle ne sont pas automatiquement répliquées dans tous les scénarios ; elles doivent être gérées dans chaque destination ou via des templates.

15. Monitoring et audit

  • CloudTrail journalise les opérations ECR.
  • Amazon Inspector fournit les findings de sécurité.
  • EventBridge peut réagir à un push ou à un scan.
  • Security Hub contrôle notamment scan, immutabilité, lifecycle et chiffrement.
  • Les tags de ressources facilitent coûts et gouvernance.

17. Questions fréquentes d’entretien

ECR ou ECS ?

ECR stocke les images. ECS orchestre et exécute les conteneurs à partir de ces images.

Pourquoi éviter latest ?

Le tag ne garantit pas quel binaire est déployé. Une version, un commit ou un digest rend le déploiement traçable et reproductible.

Comment EC2 accède-t-elle à ECR ?

Avec un IAM Role attaché à l’instance. AWS CLI/Docker obtient un token temporaire puis tire l’image ; aucune access key n’est stockée.

Comment sécuriser un repository ?

Repository privé, moindre privilège IAM, tags immuables, scan Inspector, chiffrement, lifecycle policy, CloudTrail et réplication si nécessaire.

Comment déployer une nouvelle version ?

La CI construit et pousse une image taguée par commit, puis met à jour la Task Definition ECS ou le mécanisme EC2. Les health checks valident la nouvelle version avant retrait de l’ancienne.

Différence entre image et conteneur ?

L’image est un artefact immuable stocké dans ECR ; le conteneur est une instance en exécution de cette image.

Comment retirer les anciennes images ?

Avec une lifecycle policy testée en preview, en conservant suffisamment de versions pour les déploiements et rollbacks.

18. Réponse orale en une minute

Amazon ECR est le registre managé AWS pour images Docker et OCI. Ma pipeline compile et teste l’API .NET, construit une image multi-stage, la scanne, puis l’envoie vers un repository privé en utilisant un rôle IAM temporaire via OIDC. Je tague l’image avec la version ou le SHA du commit et j’active l’immutabilité pour éviter les écrasements. ECS, EKS ou EC2 tire ensuite l’image grâce à un rôle IAM, sans clés statiques. J’active Enhanced Scanning avec Inspector, le chiffrement, CloudTrail et une lifecycle policy contrôlée pour gérer les anciennes versions. Pour un déploiement ECS, je crée une nouvelle révision de Task Definition, le service lance les nouveaux tasks et l’ALB attend leurs health checks avant de retirer l’ancienne version.
